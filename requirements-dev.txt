# Financial Model Requirements

## 1. Financial Providers

The system will support two financial providers:

* BMO
* Nesbitt Burns

There is no requirement to support additional providers at this time.

BMO and Nesbitt Burns provide Excel exports with very similar data structures.

---

## 2. Excel Imports

Financial data will be imported from Excel files exported from BMO and Nesbitt Burns.

Each Excel file represents a **snapshot of an account at a specific point in time**.

The snapshot contains information such as:

* Account number
* Snapshot date/time
* Cash balances
* Securities
* Security symbols
* Security descriptions
* Quantities
* Prices
* Market values
* Currency
* Other information provided by the brokerage

The system will preserve the imported snapshot as historical data.

### Duplicate Imports

The Excel files contain a timestamp identifying when the snapshot was generated.

The system must not import the same snapshot twice.

An import is considered a duplicate when the same provider, account, and snapshot timestamp have already been imported.

---

## 3. Accounts

The user has many accounts at both BMO and Nesbitt Burns.

Each account must be tracked independently.

An account is identified by:

* Financial provider
* Account number

Accounts will never be deleted.

Each account will have:

* Provider
* Account number
* User-defined account name

The user must be able to rename an account through the GUI.

Changing the account name must update the database.

The account name is for the user's convenience and does not affect the account's identity.

---

## 4. Account Snapshots

Every Excel import represents a complete snapshot of one account.

A snapshot represents the state of the account at that point in time.

For each snapshot, the system stores:

* Holdings
* Quantities
* Market prices
* Market values
* Cash balances
* Snapshot date/time

If a security exists in an earlier snapshot but has a quantity of zero or no longer appears in a later snapshot, the security is considered sold/removed from the later snapshot.

**Historical snapshots must never be modified.**

Example:

```text
September 1

AAPL   500 shares
MSFT   200 shares

September 15

AAPL   500 shares
```

The September 1 MSFT holding remains in the database.

The September 15 snapshot simply does not contain MSFT.

---

## 5. Portfolio Updates

The GUI will provide an **Update Portfolio** function.

When Update Portfolio is selected:

1. Use the latest holdings for every tracked account.
2. Retrieve current market prices from Yahoo Finance.
3. Calculate the current market value of each holding.
4. Calculate the current value of each account.
5. Calculate the consolidated portfolio value.
6. Store the resulting values in the database.

Updating the portfolio **does not change security quantities**.

Quantities are changed only when a new brokerage Excel snapshot is imported.

Yahoo Finance is used only to obtain current market prices.

---

## 6. Daily Portfolio History

The system must maintain historical portfolio values over time.

The system stores a maximum of **one portfolio valuation per day**.

If Update Portfolio is run multiple times on the same day:

* The earlier valuation is replaced by the latest valuation.
* Multiple valuations for the same day are not retained.

This applies to:

* Individual account values
* Consolidated portfolio value

Historical values from previous days are retained.

---

## 7. Consolidated Portfolio

The system must provide a consolidated view of all accounts.

The consolidated portfolio includes:

* All BMO accounts
* All Nesbitt Burns accounts

The user must be able to view:

* Total portfolio value
* Individual account values
* BMO totals
* Nesbitt Burns totals

---

## 8. Portfolio Graphs

The GUI will provide graphs showing portfolio value over time.

The user must be able to:

* View total portfolio value
* View individual account values
* Select which accounts appear on the graph
* Display multiple accounts simultaneously
* Filter the graph by date range

The default date range is:

**One month ago → Today**

---

## 9. Historical Date Comparison

The GUI will allow the user to enter two dates.

For each requested date, the system will select the latest portfolio valuation **on or before that date**.

The user will be able to compare:

* Total portfolio net value
* Individual account values
* Individual security positions

The comparison will show the difference between the two dates.

For securities, the comparison will include:

* Security
* Starting quantity
* Ending quantity
* Change in quantity
* Starting value
* Ending value
* Change in value

---

## 10. ROI

The system will calculate simple portfolio ROI.

ROI is based on the change in portfolio value between two dates.

The system does not currently track:

* Deposits
* Withdrawals
* Transfers

Therefore, ROI will use the simple change in value between the selected dates.

The user must be able to compare ROI between:

* Individual accounts
* BMO
* Nesbitt Burns
* Total portfolio

ROI will be displayed as a percentage.

---

## 11. Account Categorization

Each account belongs to one of the two financial providers:

* BMO
* Nesbitt Burns

The GUI will allow the user to identify and group accounts by provider.

This allows the user to compare portfolio performance between BMO and Nesbitt Burns.

---

## 12. Account Management

The GUI must allow the user to:

* View all accounts
* View the financial provider
* View the account number
* View the user-defined account name
* Rename an account

Accounts themselves are never deleted.

---

## 13. Export

The GUI must provide an option to export the consolidated financial data to Excel.

The export will be used for:

* Backup
* Sharing
* External analysis

The exported Excel file should contain the consolidated account and portfolio information stored by the application.

---

# Development Requirements

## Simplicity

The system should be implemented as simply as reasonably possible.

There is no requirement to:

* Build a generic brokerage-provider framework
* Support arbitrary financial providers
* Over-engineer the import process
* Build unnecessary abstractions
* Optimize for hypothetical future requirements

The current requirement is to support **BMO and Nesbitt Burns only**.

---

## Development Approach

Development will proceed incrementally.

Each feature should:

1. Be implemented.
2. Compile successfully.
3. Have appropriate tests.
4. Be verified before moving to the next feature.

---

## Code Requirements

When generating code:

* Always provide complete files.
* Do not provide partial code snippets unless explicitly requested.
* Keep files reasonably sized.
* Break large implementations into multiple files when necessary.
* Use type hints.
* Keep code readable.
* Avoid unnecessary abstraction.
* Avoid unnecessary future-proofing.
* Do not remove existing functionality without discussion.

The primary goal is:

**Build a working financial application that accurately preserves the user's financial history.**
